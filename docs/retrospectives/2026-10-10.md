# 2026-10-10 — What we achieved and learned

A working log, kept honest about what actually happened. Picks up where
`2026-10-08-to-10-09.md` stopped: the mini orchestrator and hand-written plans existed, `naming` and `vat`
passed as planned steps, and the next question was a full vertical slice: a REST endpoint to create a
resource (domain record, in-memory repository, service, controller). Everything below is the Implementer
only, in isolation, against hand-coded Java / Spring Boot / Maven repositories.

## Shipped

- **The widgets vertical** (`widgets-planned`): a five-step hand-written plan (domain record, repository,
  service, controller, 400 validation), a hidden HTTP acceptance test, structure checks, and a model-file
  entry for every batch.
- **Gates and hints, each from a measured failure:**
  - A scope contract for steps: `modify` (must change), `create` (exact paths), `read_only`.
  - The no-test gate now counts a class as covered when a covered changed class mentions it (a request
    record the controller test only reaches through JSON was refused, and the refusal burned the attempt).
  - An **import audit before anything is written**: a used class from another package without its import
    is refused with the exact line to add. Replayed over 591 files from steps that had passed: no false
    positive; it names every missing class in 58 of 66 recorded compile failures.
  - A compile-error import hint on retry, and an optional `declared_imports` checklist in `submit_files`
    (off by default, never swept).
  - The retry text after a compile or test failure now says the previous answer was undone.
- **Java's rules in one module** (`java.rs`: package from path, qualified names, the JDK class table, the
  audit's source analysis), so a language registry can replace it later.
- **Every batch records `mvn -version`**; the runner takes `--url`.
- **A second server with GPU-accelerated inference** (CUDA build). Same model file and flags; a step takes
  13 to 20 s instead of 55 to 90 s.

## Learned

- **Verify and refuse with the exact fix beats telling.** The import lines were in the first prompt,
  correct and complete, and the model still left the import out (4/10, no sign of help). A check before
  the build that refuses with the exact line to add took the same plan to 10/10. A refusal inside the tool
  conversation costs a tool call, not an attempt, because the model corrects it in the same conversation.
- **Harness-written text is prompt text, again.** After a failed build the harness restores the files, so
  the files the model created no longer exist. The retry text said "read the files again"; in 15 of 28
  retries after a compile failure the model went looking for files that were gone and ended in a stuck or
  budget stop. Saying the answer was undone moved that to 2 of 18 and the retry compiled 72% of the time
  (36% before). The end count stayed 7/10, because the first-attempt import was the larger cost. This is
  the second measured case of the same pattern (the earlier no-test message is the first).
- **A guard can be the failure.** The no-test gate refused a correct submission for a class tests reach
  only indirectly, and the refusal sent the model into a read loop. When a run fails, read the gate's own
  refusals before the model's code.
- **The environment is a variable.** On Java 25 Mockito cannot mock a service class (Byte Buddy), so a test
  the model wrote with `@MockBean` failed three times with an error the model could not act on. The JVM
  now sits in every batch record.
- **The plan has to state the wiring and the numbers.** Each plan fix that helped stated something the
  model had to guess: which inputs are invalid (and that a name with spaces is valid), how a test makes two
  entities with one id, the exact MockMvc setup and request body. This is a recurring cost the Planner
  inherits; it is knowledge about the stack, not about the story.
- **Easy checks first, sweeps second.** Replaying the audit over the stored runs (591 files, no
  false positives) cost no model time and settled whether it was safe to ship before a sweep.
- **Ten runs per arm cannot separate small differences.** 4/10 against 7/10 is within scatter; the audit's
  10/10 against 7/10 is a clearer step, and it is backed by a mechanism seen in the traces (21 refusals,
  all corrected in-attempt).
- **Speed changes how you work, not what is true.** The GPU server scored the same pass rates at n=3 and
  made n=10 sweeps routine; the model file keeps wall times of the two servers apart.

## Mistakes worth naming

- Advised installing gcc-14 for a CUDA 12.4 build; that toolkit supports gcc up to 13. It cost an extra
  package that then had to be removed.
- The JDK default was switched mid-sweep (the owner's change, flagged and the batch stopped); the batch
  that straddled it was discarded.
- Two changes (the undone-answer text, the `java.rs` helper tests) were written together with their
  tests, not red first.
- A clippy warning in an example was committed and fixed in the next commit.
