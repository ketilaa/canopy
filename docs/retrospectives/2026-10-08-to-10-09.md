# 2026-10-08 to 2026-10-09 — What we achieved and learned

A working log, not a polished piece: raw material for later storytelling, kept honest about what
actually happened, including the parts that went wrong.

Cross-cutting, project-level-milestone stretch: the project's central principle changed, a large
redesign was explored and dropped, and a new isolated component (the Implementer) was built from
nothing to a measured, observable, guarded state in about two days.

---

## Context

It started with a question: does Canopy use an LLM, and does it force structured output? The answer
(free-text YAML, repaired in Rust) led to the owner's real position: the rule "tool, then prompt, then
gated code" was wrong, because a small local model cannot be trusted to follow prompts. Two earlier
projects (java-harness, nexus2), which "merged could have been Canopy", were read for evidence.

That produced a long detour. A redesign of Part 1 (spec-kit inspired, one aggregate, a hand-written
golden spec, a sealed oracle, a room-booking story) was explored and then dropped by the owner as
"too much at once". The work then narrowed to one thing: the Implementer, in isolation, against an
empty Spring Boot repository, with full observability. Everything measured below comes from that.

---

## Shipped

### The principle changed (CLAUDE.md, pushed)
Escalation order is now: make the wrong answer unrepresentable (schema), look it up, verify against
ground truth and restore state, and only then teach in the prompt, with a measured delta. Rewriting the
meaning of model output stays forbidden; audits, restore, retry with specific feedback and rendering
from validated fields are allowed. Evidence recorded in `docs/design/new-course-from-java-harness-and-nexus2.md`:
a paragraph break moved a compliance probability from 0.458 to 0.058 in the predecessor, three prompt
fixes for one failure here failed identically, a same-model second opinion shares the first one's bias.
Decided but not done: deprecate the Anthropic provider (cost); retire java-harness and nexus2 by porting
knowledge, not code.

### `canopy-implementer`: an isolated crate, built test-first in layers
No dependency on any other canopy crate, so it can prove itself before being brought into `canopy-cli`.
- **Observability first.** A typed event stream (every LLM call with full wire messages, tokens, cached
  tokens, wall time and the server's own timings; every build with full output; every tool call; every
  attempt, restore and step), consumed by observers: fan-out, in-memory, a per-line-flushed JSONL trace,
  and a metrics observer. Every diagnosis below was made from the trace.
- **Build checker.** The harness, not the model, runs `mvn`. Output is digested to what a small model
  can act on. Checked against real Maven, which exposed a path bug (Maven prints the canonical path of a
  symlinked root).
- **Loop with exact restore.** A failed attempt is undone byte for byte; a retry starts a fresh
  conversation. Single-call mode and a tool mode share one write-build-restore step.
- **Tools and sandbox.** `glob`, `read_file`, `submit_files`; the model never mutates through a tool.
  Paths: no absolute, `..`, backslash, NUL, denied directories, and no symlink of any kind. Tests use
  real symlinks, loops and dangling links.
- **Gates on submission.** Read before mutate; changed production code needs a changed test that
  mentions it (a refactor step is exempt, declared by the plan, never by the model); no empty
  submission; no submission identical to disk; the third identical call ends the attempt.
- **Dogfooding.** A git-ignored `dogfooding/` of three hand-coded repositories (`java-greeter`,
  `java-naming`, `java-shop`), each with tags as starting states, seven tasks, a hidden acceptance test per
  task that fails in the starting state and passes with a discarded reference solution.
- **Model file.** The exact `llama-server` command and every measurement, with batch ids.

## Learned

- **Easy tasks teach nothing.** Thirty clean first-attempt passes, nearly identical outputs, and the
  guardrails never fired because the prompt rules were followed. Only tasks built to apply pressure
  produced a single gate firing. A guardrail that has never fired live is unverified, however good its
  unit tests.
- **Harness-authored text is part of the prompt, and it can backfire.** Three cases in one day: "you
  changed Greeter but submitted no changed test" made the model drop the Greeter change and submit only a
  test; "read the files again" was the wrong retry advice for a model that had just spent every call
  reading; a hint offering "or correct the test" is suspected of inviting a revert. Only the first is
  established (the old wording was shown 3 times in one run and produced the same wrong answer 3 times).
  The rewrite has not been tested: in the rerun the gate never fired, so `hi` going from 4/5 to 5/5 says
  nothing about it. The lesson is to measure every message the harness writes, and to check that a rerun
  actually exercises the thing it is meant to test.
- **A pass can be hollow.** Three naming runs "passed" the loop with an empty patch: the model reverted
  everything and deleted its own failing test, and no gate had anything to object to. It was caught only
  because the hidden test and the patch size disagreed. Every audit needs an adversarial counter-check,
  and "the step changed nothing" is an outcome the harness must classify itself.
- **The small model fails by avoidance, not by being wrong.** On long, multi-file submissions it stalls
  (re-reads, empty submits, twelve identical calls) or reverts, instead of answering incorrectly. That
  is a step-size limit, which points at decomposition, not at more guards.
- **A model that writes its own tests can pass them while missing the requirement** (vat: the loop passed,
  the total still excluded VAT). An independent acceptance test written up front is the structural fix.
- **Feedback delivered is not feedback used.** The retry prompt carried the exact failing test, values
  and line; the model resubmitted the same answer three times. Precision of the message was not the
  bottleneck.
- **Observability paid for itself.** Each of the findings above was one trace query away: the exact retry
  text, the twelve identical calls, the empty patch, which gate refused what.
- **A hidden test must be checked both ways:** false in the starting state, passable by a correct change.
  Both were checked for every task before any model run.
- **Memory numbers lie on macOS.** The 14B server shows 964 MB in Activity Monitor and holds 9.4 GB
  resident: memory-mapped weights are not counted. Speed came from thinking being off and short outputs,
  not from a clean context.
- **Process lessons about working together.** The golden-spec detour was too much at once and the owner
  stopped it; proposing a prompt-weakening ablation was challenged correctly (it tests a condition we would
  never ship); small steps, each approved, worked better than large ones. Mistakes of mine worth naming:
  shell and Ruby quoting corrupted a file twice (rewritten whole instead of patched again); three off-by-one
  indexes in my own tests; a leak assertion on a word that was part of a legitimate path; a lockfile change
  left unstaged and caught only later. None reached the pushed history unfixed.

## Open threads

- The no-change gate and the fast-fail are committed and seen working in one live run each; they have not
  had a full sweep.
- `naming` and `vat` fail as single steps. The owner's vision (planner from story and Gherkin, optional
  sceptic, operator approval, an orchestrator handing small steps to the Implementer, a reviewer, and
  Cucumber integration tests written up front) is the intended answer. The cheapest test of it is
  hand-written step plans for those two tasks run sequentially by a mini orchestrator. Not started.
- Gate C (new tests must fail against the old production code) is planned, not built. A shadow mode where
  gates record would-reject without enforcing would measure what they prevent. Thinking mode as an A/B on
  the hard tasks is untried.
- Anthropic deprecation, and retiring java-harness and nexus2 (including the installed `harness-cli`),
  are decided and not done.
- CLAUDE.md still says "Everything emerges. Nothing is decided upfront." That sits in tension with a
  human-chosen stack profile and an up-front plan; not yet reconciled.
- Knowledge-capture candidates: a principle ("harness text is part of the prompt; measure it") and a blog
  draft built on the hollow-pass finding were drafted and then deliberately held back until more evidence is
  in. The evidence is one clean case plus two confounded ones, and the key fix has not yet been exercised.
